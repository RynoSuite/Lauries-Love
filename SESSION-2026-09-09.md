## What changed today

### Fixed bugs, in the order they were found

1. **View on map went nowhere** (web + mobile). Web's `UserProfile` linked to
   `/map?lat&lng` but `MapPage` never read the query string, then geolocation
   re-centred on the viewer. Mobile consulted the requested member only if GPS
   failed. Mobile's fix also had to survive `MapView` never remounting — it
   sits under the profile in the Connect stack — so the focus is a one-shot
   applied on param change, on map-ready, and ahead of Android's refocus.
2. **The map now names the member** you arrived to see: a larger white-ringed
   pin with a permanent label, drawn outside the cluster group so a cluster
   bubble cannot swallow it. Only the member id travels in the URL; the name is
   looked up from map data.
3. **"Add friend" hung on your own profile.** `getRequestedFriend()` returned
   early for the current user, skipping the `finally` that is the only place
   `isLoading` clears. The friend and message controls are now absent on your
   own profile rather than permanently disabled.
4. **The Connect tab stranded on a member profile.** Opening a member from the
   wall built the Connect stack as `[DetailView]` with no map underneath, so
   the tab was stuck on that person and the map was unreachable. Cross-tab
   navigations pass `initial: false`, and an externally-opened profile pops the
   stack back to the map when it loses focus.
5. **`path.startsWith is not a function`.** The feed assigned
   `require('avatar-empty.png')` — a Metro asset **number** — onto
   `profilePicture`, a storage path, and onto the react-query cache row itself,
   so the bad value followed that member into the map and their profile.
6. **"This account may have been deleted"** about members who exist. The author
   was resolved by filtering the client's loaded list, which is one capped page
   of 500 profiles. Now falls back to fetching that one profile.
7. **Moderation counted reports for deleted content forever.**
   `moderation_queue.entity_id` is polymorphic so nothing cascades. Migration
   `20260909160000` closes them on delete and backfills.
8. **Notifications: bell counted 42, screen was empty.** Two vocabularies reach
   that screen — the database triggers write `POST_REACTION`/`POST_COMMENT`/
   `MESSAGE`/`FRIEND_REQUEST`/`FRIEND_ACCEPT`, the app's own `sendNotification`
   writes the older `NEW_*` names — and the switch ended in
   `default: return null`. Also fixed a `ReferenceError` in
   `RequestNotification` that would have crashed the screen once friend
   requests routed there.
9. **Trending sorted by nothing** on Friends and Groups: it scored
   `commentQty + commentQty` and never looked at likes.
10. **List view showed 3 people.** It filtered on
    `supportedCountryCodes.includes(user.country)` while profiles store the
    country *name*, and it read the capped 500-profile page. It is now the
    map's list: it carries the map's viewport and runs the same
    `users_in_bbox` query.
11. **Filtering by 60+ returned nothing** — see "Divergence" below.
12. **Group members screen showed "Frequently contacted" over nothing.** It
    read `group_members` by `group_id`, but an ad-hoc group conversation keeps
    its people in `conversation_members`.
13. **Avatar chips drew "?" or a blank disc.** Callers passed no `name`; the
    initials helper used `split(/s+/)` (splits on the letter s); and the
    loading overlay never cleared when there was no image, sitting on top of
    the initials as an opaque disc.
14. **Group threads drew two avatars per message**, one a bundled empty-avatar
    PNG.
15. **The Messages tab had no unread badge**, and nothing on mobile had ever
    written `last_read_at`, so any badge could only go up. Both thread screens
    now call `mark_conversation_read`.

## Next up, in order

### 1. Web/mobile field divergence — decide, then fix
The two apps write different values for the same columns:

| | web writes | mobile writes and filters on |
|---|---|---|
| `age_range` | `18-29 / 30-39 / 40-49 / 50-59 / 60-69 / 70+` | `18-34 / 35-44 / 45-59 / 60-plus` |
| `gender` | `Female / Male / Non-binary / Prefer not to say` | `female / male` |

A member who completes their profile on one app is invisible to the other's
filters — silently. Mobile's set is the likelier canon (it is what the 2,200
legacy members already use), which means editing `AGE_RANGES`/`GENDERS` in
`web/src/components/ProfileFields.tsx` and migrating existing rows.
`supabase/seed/demo_align_filter_values.sql` patched the demo members only.

### 2. Full web/mobile parity audit — before the data import
The age and gender divergence was found by accident, which means nothing else
has been checked. Audit at least: role ids, diagnosis types and subtypes,
diagnosis year, city/state/country, group visibility, notification entity
types, password rules, and what each app writes to `profiles_private`. Two
apps writing one table is only safe if they agree on every field, and the time
to find out is before 2,200 real members are in it.

### 3. A real Groups experience on mobile
Web has a directory (My groups / Groups you can join) and a group page with
that group's posts, join, leave and members. Mobile has only the
browse-and-join list in Messages, and the wall's Groups tab is a post filter
(`visibility === 'group'`), not a directory. The wall's **Explore groups**
button is a stopgap pointing at the join list; repoint it once the page exists.

### 4. SMTP2GO on Skyway's own details
Decided: our company info, not the client's domain. Jeremy to supply
credentials. Needed for password reset and for moderator alerts on reported
content. `send-email` is hardcoded to SendGrid with no account behind it.

### 5. Realtime instead of polling
The notification bell and the new Messages badge both poll on a 60s timer, so
a message arriving mid-demo takes up to a minute to appear. Both should move
to a Supabase realtime subscription together.
